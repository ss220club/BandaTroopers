Да, по этому скриншоту **текущий результат всё ещё неприемлем**. Я не буду сейчас говорить про CI/merge. По визуалу видно: система научилась проходить counters, но **не научилась строить жилое помещение как маппер**.

Я не вижу здесь “улучшенную генерацию”. Я вижу:

```text
большой shell
+ нарезанные прямоугольные области
+ повторяющиеся table/chair modules
+ слабая семантика комнат
+ пустые зоны
+ двери/маршруты без мапперской композиции
```

Ниже — анализ без попытки притянуть результат к успеху.

# 1. Что видно по скриншоту

## 1.1. Комнаты формально есть, но они не читаются как комнаты

Визуально:

* левый верхний блок выглядит как большой пустой зал с повторяющимися столами;
* левый нижний блок похож на “private”, но там тоже стоит стол/стул и несколько белых объектов; по одному PNG я не буду уверенно утверждать, что это именно кровати или сантехника;
* центральная вертикальная зона выглядит как коридор/разделитель, но воспринимается как техническая щель;
* правая часть нарезана на несколько кусков, часть из них почти пустая;
* нижняя правая/центральная зона имеет длинный пустой объём без понятной функции.

Это не “living module”. Это набор областей, куда разложили однотипные модули.

---

## 1.2. Мебель всё ещё мозаичная, только теперь формально через modules

Раньше проблема была:

```text
table
chair
table
chair
```

Теперь она стала:

```text
table+chair module
table+chair module
table+chair module
```

То есть counters могут сказать “нет loose table”, но глазами всё равно видно повторение одного и того же паттерна.

Проблема не в том, что table/chair не сгруппированы технически. Проблема в том, что **нет композиции комнаты**:

```text
одна dining/social зона
+ один focal point
+ читаемый проход
+ вторичная мебель у стены
```

Вместо этого модуль повторяется по комнате как плитка.

---

## 1.3. Нет room-level intent

Для жилого помещения должны читаться роли:

```text
entry
common/living
sleeping
sanitation
storage
optional dining/utility
```

На скриншоте я не могу уверенно прочитать:

* где главная common/social зона;
* где спальня как спальня;
* где storage как storage;
* где sanitation как отдельный приватный санузел;
* зачем нужны несколько одинаковых столов в разных местах;
* почему правые service/private зоны именно такие.

То есть semantic labels на overlay могут быть, но visual language их не подтверждает.

---

## 1.4. Слишком много пустого пола

Пустое место само по себе нормально. Но здесь это не controlled negative space. Это похоже на:

```text
не смогли осмысленно обставить комнату
→ оставили большой прямоугольник пола
```

Хороший living layout должен иметь пустое пространство как маршрут/буфер/центр комнаты. Здесь пустота часто выглядит как остаток после нарезки.

---

## 1.5. Двери технически лучше, но композиционно слабые

Двери не в углах — это уже не главный дефект. Но двери всё ещё не создают ощущение нормального маршрута:

```text
вход → entry/common → приватные/служебные помещения
```

Видно несколько дверей на центральной оси, но они не формируют понятный circulation design. Это скорее “проёмы в перегородках”, чем designed path.

# 2. Почему текущий вариант не сработал

## 2.1. Curated layer всё ещё не настоящий hand-authored layout catalog

В коде действительно появился curated layer: module catalog имеет `curated`, `curated_recipe_id`, `requires_table_pairing`, `seating_group_ok`, `max_repeat_group_per_room` и т.д.

Но сам curated catalog сейчас задаётся как список:

```dm
list("living", "dining_pair", list("table_pair", "table_corner", "desk_suite"))
list("living", "center_social_cluster", list("table_cross", "table_corner", "compact_table"))
...
```

Это не полноценные authored room scenes. Это **варианты cluster pattern’ов**, привязанные к старым cluster specs.

Иначе говоря:

```text
не "спроектировать dining room"
а "для cluster dining_pair создать несколько вариантов расстановки"
```

Этого недостаточно.

---

## 2.2. Recipes слишком примитивные

`build_curated_building_module_member_specs()` всё ещё строит паттерны простыми offsets:

* table в `(0,0)`;
* chairs вокруг по cardinal offsets;
* line по `dx = index - 1`;
* wide line по `dx = (index - 1) * 2`;
* corner через `(0,1)`.

Это не плохой низкоуровневый primitive. Но это **не room composition**.

Нужны не только offsets, а scene grammar:

```text
dining area:
  table group
  chairs
  clear side
  wall/route relation
  max one focal group per common room
  no repetition in same visual zone
```

Сейчас module знает, как поставить несколько объектов рядом. Но он не знает, **какую сцену он создаёт**.

---

## 2.3. Solver проверяет размещение, но не проектирует комнату

Candidate solver уже проверяет:

* max per building;

* max per room;

* repeat group;

* room allowed;

* door cone;

* reserved cells;

* fixture conflicts.

Это хорошо, но это всё ещё **локальная проверка объекта**.

Он отвечает:

```text
можно ли поставить этот module сюда?
```

Но не отвечает:

```text
должна ли эта комната вообще иметь такой module?
сколько focal groups допустимо в этом room role?
есть ли у комнаты readable layout?
есть ли у common один центр, а не пять столов?
```

---

## 2.4. Hard counters не измеряют главную проблему

Counters сейчас ловят:

```text
loose table
loose chair
unpaired chair
table/chair mosaic
room overfilled
route blocked
door clearance blocked
...
```

Это нужно. Но скриншот показывает дефект другого уровня:

```text
комната не имеет композиции
мебель повторяется как паттерн
роли комнат не читаются
пустое место не является осмысленным
```

То есть counters говорят: “объекты технически не нарушили правила”.

Но мапперский вопрос другой:

```text
зачем эта мебель здесь?
почему именно такая комната?
почему такой маршрут?
```

# 3. Главный вывод

Текущий подход:

```text
старые semantic zones
→ cluster specs
→ curated/generated placement modules
→ validators
```

не сможет дать хороший living layout сам по себе.

Нужен следующий слой:

```text

→ floorplan solver
→ room scene solver

```

То есть modules должны быть **последним уровнем**, а не главным мозгом генерации.

# 7. Этап 1 — Living floorplan solver

## 7.1. Только для `living`

```dm
if(archetype.id == "living")
```

Это не финальная архитектура для всех программ. Это controlled proof для самого проблемного case.

## 7.2. Living room program

Для `living` задать обязательные room roles:

```text
entry_common
sleeping
sanitation
storage
```

Optional:

```text
dining
utility
private_nook
```

`target_room_count=6` не должен насильно создавать мусорные комнаты. Правило:

```text
mandatory rooms first

target room count is soft target
```

## 7.3. Room size contracts

Минимальные контракты:

| Room role      | Min size | Preferred | Max | Комментарий                 |
| -------------- | -------: | --------: | --: | --------------------------- |
| `entry_common` |      5×5 |       6×6 | 8×8 | Основная public/social зона |
| `sleeping`     |      3×4 |       4×5 | 5×6 | Кровать + доступ + storage  |
| `sanitation`   |      2×3 |       3×3 | 3×4 | Toilet/sink, private        |
| `storage`      |      2×3 |       3×3 | 4×4 | Cabinet/rack/crate          |
| `dining`       |      3×4 |       4×4 | 5×5 | Optional                    |
| `utility`      |      2×3 |       3×3 | 4×4 | Optional                    |

Это нужно не как декор, а как hard feasibility:

```text

→ room invalid
→ candidate rejected
```

# 8. Этап 2 — Corridor/spine layout

## 8.1. Для living больше не нарезать всё BSP-подобно

Текущий результат выглядит как большие прямоугольники с вертикальной перегородкой. Нужно строить от маршрута.

Для прямоугольника около 17×17:

```text
outer shell
→ entry на requested face
→ short entry/common zone
→ central or side spine
→ private/service rooms по сторонам
```

Пример схемы, не literal layout:

```text
#################
# common/dining #
#      D        #
#----corridor---#
# sleep # bath  #
#       #       #
# store # util  #
#################
```

Или:

```text
#################
# entry/common  #
#               #
####D#####D######
# sleep # bath  #
#       # store #
#################
```

---

## 8.2. Spine rules

Hard rules:

```text
spine connects entry_common to all mandatory rooms
spine width = 1, maybe 2 if large
spine is reserved route
furniture cannot occupy spine
private rooms do not become through-routes
sanitation never used as transit
```

---

## 8.3. Door rules inside floorplan

Для living:

```text
entry/common opens to corridor or directly to private/service doors
sleeping door from corridor/common, not external
sanitation door from corridor/common, not external
storage door from corridor/common
```

Door placement must be selected from shared wall segment:

```text
shared wall length >= 3 preferred
not corner
not adjacent to another door if avoidable
clearance on both sides
```

## 9.2. `entry_common` scene

Allowed:


# 10. Этап 4 — Replace table/chair logic

## 10.1. Запрет повторных table groups в common

Нужно не просто `repeat_group`. Нужно room-scene cap:

```text
entry_common:
  social_table_group max 1
  dining_group max 1
  total table/chair focal groups max 1
```

Если хочется больше живости:

```text
one focal group
+ one side object near wall/window
```

Не:

```text
five small tables across room
```

---

## 10.2. Table/chair module should require scene slot

Сейчас module может быть разрешён zone/role. Этого мало.

Добавить:

```dm
var/scene_slot = ""
```

Примеры:

```text
social_focal
dining_focal
desk_focal
side_surface
waiting_seating
storage_run
sleep_fixture
sanitation_fixture
```

Room scene может сказать:

```text
social_focal max 1
side_surface max 1
waiting_seating max 0 for living common
```

---

## 10.3. Furniture solve order inside room

Для каждой комнаты:

```text
1. required scene modules
2. focal module
3. wall modules
4. optional secondary
5. decor
```

Если required scene не влезает:

```text
reject room/candidate
```

Не fallback scatter.

# 16. Почему это решение

## Вариант A — продолжать текущие modules и добавлять fixes

**Вероятность успеха: 20%.**

Почему плохо:

* current screenshot уже показал предел подхода;
* modules технически корректны, но композиционно бедны;
* добавление ещё recipes даст больше вариаций плохого результата.

## Вариант B — добавить room-scene layer поверх current modules

**Вероятность успеха: 70%. Предпочтительный вариант.**

Почему:

* не выбрасывает текущую работу;
* modules остаются низкоуровневым placement engine;
* новый слой решает именно проблему “зачем объект стоит в комнате”;
* можно начать только с living.

## Вариант C — полностью переписать всё сразу

**Вероятность успеха: 10%.**

Почему плохо:

* слишком большой PR;
* легко потерять provider/counter/workbench работу;
* без living proof снова получится теоретическая архитектура.

Да, по этому скриншоту текущий результат **всё ещё неприемлемый**. Не “почти готово”, не “надо CI дождаться”, а именно: **генерация визуально и мапперски не решена**.

Главная ошибка текущего направления: мы начали бороться с loose objects/counters, но не заменили принцип генерации. Сейчас система научилась ставить “валидные модули”, но эти модули всё ещё раскладываются как независимые паттерны по большой коробке. Поэтому counters могут быть зелёными, а здание остаётся мусорным.

# 1. Что видно на скриншоте без предположений

## 1.1. Это не жилое здание, а большой контейнер

На `semantic_sprites.png` видно:

* большой прямоугольный shell;
* несколько грубых внутренних стен;

* мебель разложена по большим пустым площадям, а не по комнатам;
* “common/private/service” на semantic overlay выглядит как разметка зон, а не как мапперская композиция.

Это значит: **room topology всё ещё слабая**. Не хватает настоящей планировки: entry/common → bedroom → sanitation → storage/service → optional room.

---

## 1.2. Мебель всё ещё паттернится как “стол + стул”

Даже после module layer видно повтор:

```text

стол + стул
```

Это лучше, чем полностью loose scatter, но всё ещё плохо. Почему:

* нет “один большой стол со стульями”, есть несколько одинаковых малых пар;

## 1.3. Отрицательное пространство не спроектировано

Пустота сейчас выглядит не как проход/холл/общая зона, а как “ничем не занятый пол”.

Плохой признак:

```text
много свободного пола
+ повторяющиеся маленькие группы мебели
+ нет визуального назначения комнаты
```

Маппер оставляет пустое место намеренно: под проход, обзор, центр комнаты, игровое взаимодействие. Тут пустое место выглядит как результат того, что generator не знал, что поставить.

---

## 1.4. Внутренние двери и стены не решают маршрут

Двери формально есть, но они не создают читаемую circulation-схему. По картинке не видно нормального маршрута:

```text

→ прихожая / common
→ private bedroom
→ service/sanitation
→ storage
```

Вместо этого — набор дверей в перегородках.

---

## 1.5. Окна стоят без фасадного смысла

Окна есть, но они не выглядят как результат фасадного правила комнаты:

* common получает окна не как “жилая зона”;
* private/service не читаются по окнам;
* окно не усиливает комнату;
* фасадный ритм не ощущается.

# 2. Что показывает кодовая сторона

Текущий curated layer появился, но он всё ещё построен вокруг cluster specs. В catalog есть список семей вида `living/dining_pair → table_pair/table_corner/desk_suite`, `living/center_social_cluster → table_cross/table_corner/compact_table`, и т.д.

Потом эти “curated” recipes превращаются в очень простые member offsets: стол в `(0,0)`, стулья вокруг, line/wide/grid через смещения `(index - 1, 0)`, `(index - 1) * 2`, и т.п.

Это объясняет картинку: **у нас не authored room scenes, а generic object patterns**.

Да, solver теперь проверяет `max_per_room`, `max_per_building`, `max_repeat_group_per_room`.  Но это всё равно не гарантирует хорошую комнату. Оно только ограничивает повтор конкретного module/repeat_group.

Validator ловит table/chair mosaic довольно узко: если в комнате `table_chair_count >= 4` и количество module ids слишком большое.  Но скриншот показывает, что даже несколько формально валидных малых групп могут выглядеть как процедурная мозаика.

Workbench case теперь ожидает много нулевых counters.  Но эти counters всё ещё не проверяют главное: **есть ли у комнаты читаемая сцена и мапперское назначение**.

# 3. Главный вывод

Текущий Variant A решает техническую проблему:

```text
нет loose table/chair
есть module_instance_id
есть provider audit
есть hard counters
```

Но не решает художественно-мапперскую проблему:

```text
нет room scene
нет композиции комнаты
нет нормального residential floor plan
нет правил "одна комната = одна функция + одна главная сцена"
```

Поэтому следующий шаг — не “добавить ещё modules”, а **перейти от object/module placement к room-scene placement**.

# 5. Правильное направление

## Вариант A — 75%, предпочтительный

**Сделать living-specific room-scene solver поверх текущего footprint/room layer.**

Почему:

* проблема сейчас видна именно в residential/living case;
* living — самый показательный для “живости”;
* если living не умеет комнаты/мебель/маршруты, остальные программы тоже будут выглядеть механически;
* можно не переписывать сразу весь generator;
* текущий provider/module layer можно использовать как низкоуровневую базу.

## Вариант B — 20%

Оставить текущий module solver и добавлять всё больше validation/scoring.

Почему хуже:

* уже видно, что counters могут не ловить плохую картинку;
* generic modules всё равно будут плодить однотипные паттерны;
* каждый фикс будет локальным.

## Вариант C — 5%

Использовать готовые DMM-room chunks и склеивать комнаты prefab’ами.

Почему хуже:

* быстро даст красивее, но потеряет универсальность размеров;
* сложно адаптировать под arbitrary footprint;
* будет плохо масштабироваться на разные программы.

**Выбор: Variant A, но не текущий “Variant A modules”, а новый слой `room_scene_solver`.**

# 6. Новый принцип генерации

Сейчас:

```text

→ module
```

Нужно:


То есть generator должен сначала решить:

А потом выбрать **одну главную сцену** для каждой комнаты.

# 13. Как валидировать visual quality без OCR и без субъективности

## 13.1. Room identity

```dm
/proc/validate_room_identity(state, room)
	var/role = room.role
	var/primary_scene_count = count_primary_scenes(room)

	if(role in list("private", "sleep_privacy") && !has_scene(room, "bedroom"))
		private_room_without_bed_scene_count++

	if(room.zone_id == "sanitation" && !has_scene(room, "sanitation"))
		sanitation_without_sanitation_scene_count++

	if(room.zone_id == "storage_service" && !has_scene(room, "storage"))
		storage_without_storage_scene_count++

	if(!primary_scene_count && room.area >= 6 && !(room.role in list("route", "entry")))
		room_identity_missing_count++
```

## 13.2. Common fragmentation

```dm
/proc/validate_common_scene_fragmentation(state, room)
	if(room.zone_id != "common")
```

# 19. Итог

Текущий результат плохой не потому, что не хватает объектов.
Он плохой потому, что generator всё ещё думает категориями:

```text
cluster/module/object
```

А должен думать категориями:

```text
room/scene/function/composition
```

Следующий правильный шаг: **living room-scene solver + scene validators**, а не расширение текущих generic modules.










Да. Предыдущий `living-only room scene solver` **не является полным ответом на универсальную генерацию**. Он полезен как минимальный proof, но если делать правильно, нужен **универсальный слой паттернов и правил**, где `living` — только первый набор данных, а не отдельная логика на костылях.

Сейчас новый коммит не выглядит как универсальный переписанный генератор. По diff между `f0199a4` и текущим `8487739` изменены в основном текущие файлы `building_layout_*`, module catalog, validators, archetypes, fixture/state, удалён `user_test.json`; отдельного нового универсального layout/scene/pattern engine в списке изменений не видно.

Текущий pipeline всё ещё строится через staged mutable flow:

```dm

spatial_partition
room_shapes
geometry
derived_walls
semantic_rooms
anchors
semantic_slots
infrastructure
interiors
fixtures
clutter_detailing
facade
validation
microvariation
macros
scoring
```

А curated modules всё ещё создаются из `archetype + cluster_spec + recipe_id`, то есть это слой над старыми cluster specs, а не полноценная универсальная система room scenes/patterns.  Сами recipes строят простые offsets: table/chairs, seating row, lines, corners.  Это объясняет, почему картинка остаётся плохой: **генератор ставит валидные объектные паттерны, но не проектирует комнату**.

# 8. Универсальный scene solver

## 8.1. Entry point

```dm
/datum/world_edit_generator/building_layout/proc/solve_building_v2_scenes(context, candidate)
	var/list/scene_instances = list()

	for(var/datum/world_edit_building_room_plan/R as anything in candidate.room_plans)
		var/list/scenes = get_scene_candidates_for_room(context, R)
		var/datum/world_edit_building_scene_plan/best_scene = select_best_scene_for_room(context, candidate, R, scenes)

		if(!istype(best_scene) && room_requires_primary_scene(context, R))
			candidate.errors += "scene.required_missing:[R.id]"
			continue

		if(istype(best_scene))
			if(!commit_scene_plan(context, candidate, R, best_scene))
				candidate.errors += "scene.commit_failed:[R.id]"
				continue
			R.scene_plan = best_scene
			scene_instances += best_scene

	return !length(candidate.errors)
```

---

## 8.2. Scene selection

```dm
/proc/select_best_scene_for_room(context, candidate, room, scenes)
	var/best_score = -999999
	var/datum/world_edit_building_scene_plan/best = null

	for(var/datum/world_edit_building_scene_contract/S as anything in scenes)
		if(!scene_contract_can_fit_room(context, room, S))
			continue
		var/datum/world_edit_building_scene_plan/plan = build_scene_plan(context, candidate, room, S)
		if(!istype(plan))
			continue
		var/score = score_scene_plan(context, candidate, room, plan)
		if(score > best_score)
			best_score = score
			best = plan

	return best
```

## 11.1. Scene identity validator

```dm
/proc/validate_room_scene_identity(context, candidate)
	for(var/datum/world_edit_building_room_plan/R as anything in candidate.room_plans)
		var/datum/world_edit_building_room_contract/C = context.program_contract.get_room_contract(R.contract_id)

		if(!istype(C))
			continue

		if(C.required && !istype(R.scene_plan) && length(C.required_scene_kinds))
			context.validation.room_primary_scene_missing_count++

		if(R.role == "sleeping" && !room_has_scene_kind(R, "bedroom"))
			context.validation.private_room_without_bed_scene_count++

		if(R.role == "sanitation" && !room_has_scene_kind(R, "sanitation"))
			context.validation.sanitation_without_sanitation_scene_count++

		if(R.role == "storage" && !room_has_scene_kind(R, "storage"))
			context.validation.storage_without_storage_scene_count++

		if(R.area() >= 12 && !istype(R.scene_plan) && !(R.role in list("route", "entry")))
			context.validation.room_identity_missing_count++
```

```dm
/proc/validate_common_scene_fragmentation(context, candidate)
	for(var/datum/world_edit_building_room_plan/R as anything in candidate.room_plans)
		if(!(R.role in list("entry_common", "common", "dining")))
```

# 14. Почему это лучше текущего module-only подхода

Текущий module-only решает:

```text
куда можно поставить объектную группу?
```

Новый scene/pattern solver решает:

```text
какая комната нужна?
какой у неё размер?
как она связана маршрутом?
какая сцена делает её читаемой?
какие объекты нужны для этой сцены?
```

Это и есть универсальная генерация.
