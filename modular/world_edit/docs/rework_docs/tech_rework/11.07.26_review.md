# Вердикт

Предварительный анализ агента в основном верный. Текущая генерация — **false-green**: pipeline уже не разваливается технически, но архитектурная модель остаётся слабой.

Последний head PR — `1fb3d7d3a69228e28a0ef335afb3628c09ec5263`. Старые staged/V2-пути действительно удалены, а production использует один канонический solver. Это правильное решение, и его нужно сохранить: **никаких `v3`, `solver_next`, новых feature flags или параллельного fallback pipeline**.

Но заявленное в документации завершение преждевременно: там уже зафиксированы `15/15 ready`, ручной visual review и отсутствие нерешённых проблем, хотя новые скриншоты это опровергают. Статус acceptance необходимо вернуть в `IN PROGRESS`.

# 1. Что именно сломано в текущей реализации

## 1.1 Топология фактически одна

Для всех программ сейчас разрешены только:

```dm
list("adaptive_axis", "adaptive_cross_axis")
```

Оба варианта вызывают один `build_building_layout_axis_region_candidate()`: строят двухклеточную прямую полосу и две области по сторонам. Для прямоугольного footprint дополнительная crossbar вообще не создаётся. Поэтому workshop, laboratory, kitchen, dormitory и living различаются содержимым, но не архитектурой.

Это главный корень однообразных скриншотов.

---

## 1.2 Семантическая adjacency graph компилируется, но не управляет layout

`compile_building_layout_connection_contracts()` переносит adjacency rules из semantic plan в program contract. Однако topology builder затем не использует эти связи и просто подключает **каждую комнату непосредственно к `"route"`**.

То есть заявленный pipeline:

```text
semantic adjacency → topology
```

фактически работает как:

```text
semantic rooms → каждая комната к центральному коридору
```

---

## 1.3 Маршрут строится раньше помещений и диктует всё здание

Сейчас `allocate_building_layout_rooms()` сначала вызывает:

```dm
solve_building_layout_route_from_region()
```

и только после этого размещает комнаты.

Дополнительно `find_best_building_layout_room_rect_for_contract()` немедленно возвращает первый приемлемый direct-route rectangle и даже не сравнивает его с другими типами размещения.

Это структурно закрепляет результат:

```text
коридор сначала
→ комнаты прижимаются к коридору
→ стены оборачивают прямоугольники
→ cleanup удаляет хвосты
```

Никакие дополнительные score penalties полностью это не исправят.

---

## 1.4 `target_room_count` достигается за счёт circulation zones

Program contract сначала собирает все required zones, включая `entry`, `route`, `choke`, а затем добивает список до `target_room_count`. Для каждой demand создаётся полноценный room contract.

Поэтому:

```text
target_room_count = 7
```

может означать:

```text
5 функциональных помещений
+ entry_buffer
+ central_aisle
```

Это не соответствует пользовательскому понятию количества комнат.

---

## 1.5 Повторные room instances намеренно лишены primary composition

Текущий ownership-код возвращает `FALSE` для любого `room.instance_index > 1`. Кроме того, required cluster specs пропускаются для повторных instances.

Это прямо объясняет:

* первый sleep bay получает четыре кровати;
* повторный sleep bay получает одну fallback-кровать;
* первый storage получает полноценную группу;
* `parts_storage_2` получает один rack.

Это не проблема случайных весов. Это текущий контракт ownership.

---

## 1.6 Scene hierarchy пока номинальная

`scene_contract` уже содержит:

```dm
primary_modules
secondary_modules
detail_modules
primary_anchor_policy
negative_space_policy
```

Но room plan хранит один `scene_plan`, а solver выбирает только одну лучшую сцену на комнату. Последующий optional pass лишь отбрасывает или добавляет отдельные members.

Также canonical scene path размещает cluster specs напрямую по anchor tiles и отдельно special-case-ит table cluster. Он не использует authored `occupied_offsets`, `clearance_offsets` и `member_specs` из placement module catalog как атомарную композицию.

При этом полноценный curated module catalog уже существует и содержит групповые footprints, clearance и table/chair recipes.

---

## 1.7 Underfill validator формально разрешает почти пустые комнаты

Текущие минимумы:

```text
route / entry → 0
storage       → 1
прочие >=16  → 2
прочие <16   → 1
```

А `large_sparse_room_count` начинает работать только при площади `>=64`.

Поэтому:

* два светильника в entry room;
* два стула в dining room;
* один rack в storage room;
* table + chair в большой kitchen prep room

формально проходят.

---

## 1.8 Underfill, template failures и cleanup не являются hard failures

Hard-failure predicate отклоняет doors, missing scenes, blocked negative space и некоторые topology defects, но не отклоняет по:

* `layout_underfurnished_room_count`;
* `large_sparse_room_count`;
* `layout_scene_underfill_count`;
* excess template rejects;
* wall cleanup removals.

Template reject validator только копирует два raw counters, не связывая их с провалом required composition.

---

## 1.9 Canyon detector не видит двухклеточный коридор

Он проверяет стены непосредственно на соседних клетках каждой route tile. У двухклеточной полосы один сосед — другая route tile, поэтому canyon не определяется.

# 2. Выбранное решение

## **Graph-first переработка текущего canonical solver**

**Предпочтение: 92%.**

Оставшиеся **8%** — продолжать латать axis scoring, underfill thresholds и cleanup limits. Это дешевле, но фундаментально не исправит одинаковую структуру всех программ.

Целевой pipeline:

```text
Semantic Plan
→ Space Classification
→ Functional Room Graph
→ Topology Family Candidates
→ Graph-aware Room Allocation
→ Route Network / Open Aisles
→ Partition Graph
→ Openings and Direct Wall Materialization
→ Per-instance Composition Contracts
→ Atomic Placement Modules
→ Hard Quality Trial
→ Emit
```

Это остаётся **одним текущим solver**, без версий и параллельных режимов.

# 6. Перестроить порядок allocation

## Сейчас

```text
route first
→ rooms around route
```

## Должно быть

```text
topology graph
→ root/hub/open bay
→ adjacent child rooms
→ nested/service rooms
→ access ports
→ minimal route network
```

Новый entrypoint:

```dm
/datum/world_edit_generator/building_layout/proc/allocate_building_layout_rooms(
	datum/world_edit_building_layout_context/context,
	datum/world_edit_building_layout_region_candidate/region_candidate,
	allocation_variant = 0
)
	var/datum/world_edit_building_layout_candidate/root = new
	root.topology_graph = region_candidate.topology_graph

	var/list/beam = list(root)

	for(var/datum/world_edit_building_layout_topology_node/node as anything in get_building_layout_node_order(root.topology_graph))
		beam = expand_building_layout_allocation_beam(
			context,
			beam,
			node,
			6, // beam width
		)

		if(!length(beam))
			return null

	var/datum/world_edit_building_layout_candidate/candidate = select_best_partial_layout(beam)

	if(!solve_building_layout_route_network(context, candidate))
		return null

	if(!solve_building_layout_openings(context, candidate))
		return null

	return candidate
```

Ограничения:

```text
beam width: 6
top rectangles per node: 8
candidate expansions: <= 96 per topology
total topology candidates: <= 24
route expansions: existing bounded limit
```

---

## 6.1 Убрать ранний direct-route return

Нельзя делать:

```dm
if(direct_route_rect)
	return direct_route_rect
```

Direct-route rectangles должны быть обычными candidates, сравниваемыми с:

* shared-wall parent candidates;
* nested candidates;
* perimeter candidates;
* open-bay candidates;
* privacy-biased candidates.

---

## 6.2 Не перебирать dimensions от `1×1`

Текущий bounded loop может исчерпать 128 candidates до рассмотрения лучших крупных размеров.

Генерировать только разумные dimension variants:

```dm
list(
	ideal_w × ideal_h,
	ideal_h × ideal_w,
	min_w × ceil(target_area / min_w),
	ceil(target_area / min_h) × min_h,
	ideal_w ± 1,
	ideal_h ± 1,
)
```

Сначала проверять размеры около preferred area, потом compact variants.

# 7. Route network вместо центральной полосы

## 7.1 Route должен соединять access ports

После room allocation:

1. Создать entry access point.
2. Создать access ports функциональных помещений.
3. Сохранить прямые room-room edges, если adjacency допускает shared/open transition.
4. Строить route только для edges, которым реально нужен corridor.
5. Соединить access points через bounded A* по незанятым tiles.
6. Минимизировать:

   * route area;
   * количество turns;
   * dead ends;
   * проходы вдоль всей длины здания.

---

## 7.2 Open-bay aisle — overlay, а не отдельная стенами окружённая комната

Для workshop, dormitory, hydroponics, storage:

```dm
/datum/world_edit_building_layout_candidate
	var/list/route_overlay_turfs = list()
	var/list/route_floor_turfs = list()
```

`route_overlay_turfs` могут находиться внутри open-bay room:

```text
room ownership сохраняется
route overlay запрещает мебель
стены между room и aisle не создаются
```

Это позволит получить:

* workshop bay с рабочим проходом;
* dormitory sleep bay с центральным aisle;
* hydro rows с проходом;
* storage aisles между racks,

вместо corridor canyon.

## 9.3 Placement

```dm
/datum/world_edit_generator/building_layout/proc/solve_building_layout_module_instance(
	datum/world_edit_building_layout_context/context,
	datum/world_edit_building_layout_candidate/layout_candidate,
	datum/world_edit_building_layout_room_plan/room,
	datum/world_edit_building_layout_scene_plan/scene,
	datum/world_edit_building_cluster_spec/cluster_spec,
	list/occupied_lookup
)
	var/datum/world_edit_building_placement_module_catalog/catalog = get_building_placement_module_catalog()
	var/list/modules = catalog.get_for_cluster(cluster_spec)

	var/list/candidates = list()

	for(var/datum/world_edit_building_placement_module/module as anything in modules)
		if(!building_layout_module_allowed_in_room(module, context, room))
			continue

		for(var/rotation in GLOB.cardinals)
			for(var/turf/anchor as anything in get_building_layout_module_anchor_turfs(context, layout_candidate, room, module))
				var/datum/world_edit_building_layout_module_candidate/candidate = build_building_layout_module_candidate(
					context,
					layout_candidate,
					room,
					module,
					anchor,
					rotation,
					occupied_lookup,
				)

				if(istype(candidate))
					candidates += candidate

	var/datum/world_edit_building_layout_module_candidate/best = select_best_building_layout_module_candidate(candidates)
	if(!istype(best))
		return FALSE

	return commit_building_layout_module_candidate(scene, cluster_spec, best, occupied_lookup)
```

Все members должны ставиться или отклоняться **целиком**.

# 11. Area-relative quality

Raw object count недостаточен. Нужны три значения на комнату:

```text
module_instance_count
functional_unit_count
occupied_tile_ratio
```

Пример role defaults:

| Role               |                                              Minimum |
| ------------------ | ---------------------------------------------------: |
| public / dining    |                         1 focal module и 8% occupied |
| hub / work         |            1 major + 1 support module и 10% occupied |
| private / sleeping | capacity из composition, обычно 1 unit на 8–12 tiles |
| storage / service  |         1 authored run на 10–12 tiles и 14% occupied |
| secure / lab       |                 1 functional machine group + support |
| circulation        |                                      0 dense objects |


# 12. Wall materialization без cleanup как штатного этапа

## 12.1 Стены строить из partition graph

Для соседних floor cells с разными owners:

```text
same owner              → no wall
open merge              → no wall

```

То есть:

```text

```

```text

```

# 13. Исправить canyon detector по route band

Алгоритм:

1. Найти connected route component.
2. Для каждой tile определить локальную orientation по route neighbors.
3. Пройти перпендикулярно через всю ширину route band.
4. Найти **первую non-route tile** с обеих сторон.
5. Если обе являются стенами и там нет public opening — это canyon slice.
6. Сгруппировать последовательные slices.

```dm
/datum/world_edit_generator/building_layout/proc/count_building_layout_route_band_canyon_slices(
	datum/world_edit_building_layout_candidate/candidate,
	list/wall_lookup
)
```

Hard rule:

```text
max continuous canyon run <= 3
canyon share <= 30% main route
```

Это поймает и двухклеточные коридоры.
