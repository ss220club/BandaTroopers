# Canonical Building Layout Solver

## Статус

`building_layout` использует один production pipeline для всех программ. Runtime-переключателя и альтернативного staged layout path нет.

Поддерживаемые программы:

`living`, `workshop`, `storage`, `checkpoint`, `medbay`, `hydroponics`, `kitchen`, `dormitory`, `office`, `security`, `chapel`, `ritual_chamber`, `compound_colony`, `engineering`, `laboratory`.

Публичный контракт сохранён:

- generator id: `building_layout`;
- формы: `point`, `rectangle`, `filled_rectangle`;
- четыре UI-поля программы, shell/style, размера и направления;
- стабильные seed/direction/size semantics;
- preview/apply/undo через существующий World Edit transaction layer.

## Канонический pipeline

```text
Program Contract
→ Pattern Fields
→ Room Allocation
→ Route + Access Reservations
→ Openings / Windows
→ Partitions / Walls
→ Scene Hierarchy
→ Placement Modules
→ Trial Quality Selection
→ Emit
```

Archetype/semantic catalog является единственным источником различий программ. Solver не содержит отдельных coordinate recipes для living или других программ.

## Контракты комнат и точное количество

Каждая zone компилируется в room contract с:

- min/preferred/max area и aspect bounds;
- required/optional/repeated instances;
- privacy и route-touch policy;
- partition/opening/window policy;
- scene capacity и module ownership.

`target_room_count` является точным контрактом. Дополнительные комнаты создаются как семантически оправданные повторные instances. Произвольные divider rooms не используются. Невозможный запрос возвращает `program.target_room_count_unreachable`.

Поиск ограничен:

- максимум 24 layout candidates;
- максимум 128 room candidates на demand;
- route search — не более `min(4 × footprint_count, 4096)` expansions;
- максимум 64 anchors и 32 placement candidates на module.

## Route и access reservation

Route строится относительно уже размещённых комнат и не проходит через private/service semantic rooms.

Каждая route-touch room хранит структурированную reservation:

```text
room_id + wall_run + route_run + connector_run
```

Controlled door требует side-run шириной 3. Центральный turf используется как opening; segment ends недопустимы. Public arch/wide-arch требует ширину не менее 2. Allocator резервирует wall/route runs до размещения следующих комнат, поэтому поздний opening solver не может получить геометрически недоступную комнату.

Semantic route rooms (`service_aisle`, `central_aisle` и аналоги) материализуются как свободная reserved route area и не меблируются.

## Openings, partitions и walls

Opening solver выбирает реальный shared-wall segment:

- public/open rooms — arch или wide arch без door object;
- private/service rooms — controlled door;
- secure rooms — secure-door policy;
- corner controlled doors запрещены;
- public opening width меньше 2 запрещена.

Walls строятся из ownership/partition graph. Public merge не создаёт лишнюю разделительную стену. Physical door emitter обрабатывает только openings, которым действительно нужен door object.

## Scene hierarchy и budgets

Scene generation не использует dispatch по scene contract id. Catalog clusters компилируются в generic module patterns.

Порядок размещения:

1. required/signature identity modules всех комнат;
2. door-to-focus negative space;
3. secondary/detail modules из остатка global budget.

Compact substitutes являются альтернативой primary module, а не дополнительным major module. Module ownership отдаёт приоритет explicit optional zone, затем ordered exact zone anchors и только затем generic anchor tags. Повторные rooms не дублируют primary signature zone.

Объект не может занимать route, opening cone, negative space или чужую semantic room.

## Hard quality gates

Каждый candidate проходит trial emission до выбора. Candidate отклоняется при:

- недостающей комнате, required connection, primary scene или required module;
- неправильном shared wall, corner/short opening или window policy;
- thin/bad-aspect room;
- пустой большой semantic room;
- blocked route или negative space;
- object ownership/semantic-room violation;
- wall topology defect;
- program/module budget overflow.

Архитектурные gates:

- public rooms не hard-closed;
- corridor canyon excess = 0;
- opposing route door pairs ≤ 1;
- required module placement успешен;
- template geometry и missing-wall-context rejects ≤ 80;
- standard cases имеют минимум два hard-valid candidates.

Канонические metadata используют `layout_*`, например:

- `layout_pattern_id`;
- `layout_candidate_id`;
- `layout_candidate_count`;
- `layout_hard_valid_candidate_count`;
- `layout_scene_count`;
- `layout_public_opening_missing_count`.

`structured_scene_owner` имеет значение `building_layout`.

## Acceptance evidence

Обычный (не isolated) visual workflow прошёл единой матрицей:

- target-room cases: living, storage, workshop, office, hydroponics, dormitory;
- representative cases: checkpoint, medbay, kitchen, security, chapel, ritual_chamber, compound_colony, engineering, laboratory;
- результат: `15/15 ready`, `rendered=15`, `failures=0`;
- compile: `BUILD.cmd --ci dm -DUNIT_TESTS`, 0 errors, 0 warnings.

`tools/world_edit_visual` остаётся observer/reporting surface и не исправляет production geometry.

## Финальная verification

- targeted canonical unit tests прошли; полный unscoped unit run превысил десятиминутное окно, при этом найденный им out-of-bounds в door-cone loop исправлен, а повторные targeted tests зелёные;
- living point N/S/E/W, rectangle N/S/W и compact/standard/spacious прошли ordinary workflow;
- same-seed replay совпал по layout, footprint, room graph, route, walls и pattern credits;
- вручную просмотрен semantic sprite каждой из 15 программ; semantic rooms имеют primary identity, а route/entry/hub negative space остаётся свободным;
- production/tests/cases не содержат удалённых V1/V2 aliases, staged generation types, legacy divider/layout/fixture entrypoints или `switch(scene_contract.id)`;
- `git diff --check` проходит.
