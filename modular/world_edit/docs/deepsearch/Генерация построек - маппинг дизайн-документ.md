# Генерация построек - маппинг дизайн-документ

> Статус: обязательный implementation contract для переработки `building_layout` в текущем PR.
>
> Назначение: зафиксировать, как генератор построек обязан мыслить маппингом SS13/BYOND, а не просто собирать оболочку и расставлять предметы. По этому документу нужно реализовывать и принимать текущий PR.
>
> Важно: PR не считается завершенным, если нарушены `MUST`, `REJECT` или acceptance gates ниже. Если часть требований технически не реализуется в этом PR, она должна стать `UNSUPPORTED_WITH_CLEAR_ERROR`, не рекламироваться как поддержанная в UI и не засчитываться acceptance-метриками.

## 0. Как читать документ

Документ устроен как контракт текущего PR, а не как обзор идей. Сначала идут правила чтения и навигация, затем доказательства и общий pipeline, потом отдельные правила геометрии, комнат, паттернов, программ, валидации и аудита.

Если при реализации возникает конфликт между “красивым результатом” и `MUST`, побеждает `MUST`. Если хочется заменить требование частичным fallback-ом, это должно быть явно отражено в task-state contract и согласовано отдельно.

`MUST`: документ описывает критерии реализации текущего PR. Он не является списком “идеального будущего”.

`REJECT`: писать “поддерживается” для программы, формы или паттерна, если она только названа в metadata, но не имеет реальной генерации, validator credit и golden seed/batch coverage.

### 0.1. Степени строгости

Чтобы этот документ нельзя было трактовать как набор пожеланий, все требования делятся на уровни.

| Уровень | Значение |
| --- | --- |
| `MUST` | Обязательный контракт. Если нарушен, генерация не считается валидной. |
| `SHOULD` | Должно выполняться по умолчанию; отклонение требует явного решения в `DECISIONS.md` или отдельной причины в debug report. |
| `MAY` | Допустимая вариативность, если она не ломает `MUST`. |
| `REJECT` | Запрещенный подход. Не может закрывать задачу без отдельного согласия пользователя. |

### 0.2. Definition Of Done для документа

```text
1. Для каждого публичного shape есть buildable policy и failure policy.
2. Для каждой программы есть mandatory rooms, mandatory patterns, compact/normal/large variants.
3. Для каждого mandatory pattern есть semantic credit и clear failure rule.
4. Для маршрутов, стен, дверей, anchors и DIR есть проверяемые инварианты.
5. Для текущего PR есть traceability: design rule -> datum/proc/metadata/validator/quality check.
```

### 0.6. One-PR implementation model

Работа выполняется одним PR, но делится на независимые workstreams/sub-agents. Каждый workstream обязан отдавать результат через общий integration contract:

```text
datums/procs/metadata не конфликтуют;
validator может проверить результат;
debug report показывает реальные stage outputs;
acceptance checks покрывают изменения;
стадия не обходит обязательный pipeline через локальный fallback.
```

| Workstream / sub-agent | Зона ответственности | Выход | Блокирующие acceptance gates |
| --- | --- | --- | --- |
| `architecture_agent` | ProgramSpec, RoomSpec, ZoneSpec, shared state | datums, contracts, stage reports | no `building_layout_v2`, no fake metadata |
| `evidence_agent` | аудит локальных `.dmm`, подтверждение паттернов | `EVIDENCE.md`, `rg` commands, typepaths, coordinates/screens | map claims reproducible |
| `shape_agent` | footprint/envelope для всех UI shapes | buildable envelope или clear error | no silent fallback, no random bite for rectangle |
| `room_planner_agent` | room/zone packing, compact/normal/large | solved rooms/zones | mandatory rooms have bounds/access |
| `corridor_agent` | reserved_walk, main route, loading/work aisles | route graph, corridor report | all mandatory rooms reachable |
| `wall_door_agent` | tile-based walls, doors/airlocks | wall plan, door report | no double walls, no diagonal-only contacts |
| `anchor_agent` | anchors, DIR, object placement slots | anchor catalog | mandatory anchors exist |
| `pattern_agent` | mandatory/secondary patterns | PatternSpec, placed pattern reports | mandatory patterns actually placed |
| `program_agent` | visible program contracts and recipes | compact/normal/large recipes | each visible program has real signature patterns |
| `infrastructure_agent` | APC, air alarm, lights, areas, wall machinery | infrastructure pass | infrastructure is anchored and route-safe |
| `validation_agent` | validators, semantic credits, repair limits | validation reports | credit granted only by validator |
| `debug_quality_agent` | preview overlay, golden seeds, batch metrics | debug UI/report, tests/checks | screenshots are supporting evidence only |
| `integration_agent` | merge, old path audit, final gates | final reports | forbidden fallback counters = 0 |

`MUST`: sub-agent/workstream может реализовывать свой слой, но не может обходить обязательные стадии через fallback.

`MUST`: `integration_agent` проверяет, что все стадии работают в одном pipeline.

`REJECT`: отдельный мини-генератор, который не проходит общий validation/debug contract.

## Часть A. Контракт генератора

### 1. Главная формула

Генератор обязан строить не набор объектов, а мапперскую композицию:

```text
Здание = программа + стиль + корпус + комнаты + маршруты + стены + двери + паттерны + детали + валидация.
```

Program validity is not object count. Program validity is:

```text
real rooms/zones
+ real reserved route
+ tile-valid walls/doors
+ real anchors
+ emitted mandatory patterns
+ validator-granted semantic credits
+ SS13 infrastructure/access sanity
+ debug evidence
+ batch acceptance.
```

`MUST`: generated building is invalid if the user can identify its program only by reading the UI dropdown.

Минимальная формула для реализации:

```text
ProgramSpec
  -> RoomSpec graph
  -> footprint/envelope policy
  -> room packing
  -> mandatory corridor graph
  -> single-thickness wall builder
  -> doors/airlocks at crossings
  -> anchor extraction
  -> mandatory room patterns
  -> secondary patterns by room area
  -> detail/clutter pass by slider
  -> validation/debug report
  -> emit preview/apply actions
```

Рандомность должна выбирать среди валидных архитектурных решений. Она не должна напрямую решать, где стоит кровать, есть ли проход к выходу, есть ли санузел в жилом модуле, или будет ли медбей иметь лечение и хранение.

### 1.1. Таблица стадий solver-а

Каждый этап должен иметь вход, выход, validation gate и metadata. Если этап не может выполнить `MUST`, он не должен тихо подменяться следующим этапом.

| Stage | Input | Output | Validation gate | Allowed fallback | Required metadata |
| --- | --- | --- | --- | --- | --- |
| Normalize request | UI params, placement context | canonical request/contract | program/style/shape known | none | `program_id`, `shell_preset`, `shape_id`, `direction` |
| Footprint/envelope | request, shape mask | buildable envelope | connected, room-capable, one z-level | compact envelope only if shape contract preserved | `footprint_source`, `envelope_family`, `usable_area` |
| Semantic plan | ProgramSpec, style capabilities | rooms/pattern requirements | mandatory rooms/patterns declared | none | `semantic_requirements`, `style_capabilities` |
| Room packing | envelope, RoomSpecs | solved rooms | room min sizes, no invalid 1x1 normal rooms | compact variant only if declared | `room_reports`, `room_attempt_count` |
| Corridor/reserved_walk | rooms, main exit | route graph | reaches all required rooms | none for mandatory rooms | `corridor_report`, `reserved_walk_count` |
| Doors/openings | route graph, room boundaries | airlocks/openings | door cones clear | alternate door edge | `door_reports` |
| Walls/floors | floor ownership, room edges | single-thickness wall plan | no double/diagonal invalid walls | repair only before fixtures | `wall_report`, `corner_report` |
| Anchors | rooms, walls, route | anchor catalog | mandatory anchors exist | fallback anchors only for optional/secondary | `anchor_counts` |
| Semantic slot preflight | patterns, anchors | reserved slots | no shortage/conflict for mandatory | none for mandatory | `semantic_slot_reports` |
| Infrastructure | style, anchors | APC/alarm/lights/etc | required infrastructure placed | explicit exemption only | `infrastructure_report` |
| Major patterns | mandatory slots | functional fixtures | semantic credits satisfied | compact mandatory pattern only if declared | `pattern_reports` |
| Secondary patterns | room budgets | useful extra fixtures | no route blockage | skip allowed | `secondary_reports` |
| Facade | envelope, program, style | exterior grammar | entry/service/public faces valid | simpler facade allowed | `facade_report` |
| Validation/repair | full state | valid candidate or failure | no blocking errors | bounded repair only before acceptance | `validation_errors`, `repair_reports` |
| Microvariation | valid layout | decor/noise | cannot break validity | skip allowed | `microvariation_count` |
| Score/select | candidate reports | chosen candidate | score ranks only valid candidates | retry within cap | `layout_candidate_reports` |
| Emit plan | chosen state | preview/apply actions | emitted metadata matches validated state and passes post-emit validation | none | `building_placement_contract`, `layout_hash`, `post_emit_validation_error_count` |

### 1.2. Stage-to-code mapping

This table is an implementation guardrail. Current PR implementation work must change the current call path, not wrap it with validator-only fixes.

Current orchestration entrypoint: `build_building_layout_candidate_state()` in `world_edit_generator_building_layout.dm`.

| Target stage | Current surface | Required change |
| --- | --- | --- |
| Normalize request | `building_layout_request.dm`, `world_edit_generator_building_layout.dm` UI/config readers | Add canonical `building_placement_contract` fields: `program_id`, `shell_preset`, `shape_id`, `direction`, `footprint_source`, `usable_area`, `size_policy`. |
| Footprint/envelope | `resolve_shape_footprint()`, `validate_footprint()`, `building_layout_footprints.dm` | Public shape must determine envelope. `POINT` may use half-size; other shapes must use user mask/bounds/path. |
| Semantic plan | `build_building_semantic_plan()` / archetype setup in `building_layout_archetypes.dm` and `building_layout_programs_extra.dm` | Declare mandatory rooms, mandatory patterns and semantic credits before geometry/fixture placement. Raw `category_minimums` becomes density only. |
| Room packing | `building_layout_geometry.dm` region/patch-room code | Replace patch/percent fallback with solved rooms that have role, bounds, access point and tier. |
| Corridor/reserved_walk | `building_layout_geometry.dm` route/region helpers | Build primary route before anchors/fixtures; all mandatory rooms must connect to route. |
| Doors/openings | `building_layout_geometry.dm`, emitter door actions | Corridor crossing through separator creates door/opening and reserves door cone. |
| Walls/floors | `building_layout_geometry.dm`, `building_layout_emitter.dm` | Emit single-thickness wall turfs from floor ownership edges and exterior envelope, not independent room boxes. |
| Anchors | `extract_building_anchors()` in `building_layout_anchors.dm` | Extract anchors from solved room/wall/route model; mandatory anchors cannot be synthetic fallback-only. |
| Semantic slot preflight | `run_building_semantic_slot_preflight()` | Reserve mandatory semantic slots atomically before infrastructure and fixtures. |
| Infrastructure | `place_building_infrastructure()` | Write canonical ledger IDs: `infrastructure_apc`, `infrastructure_air_alarm`, `infrastructure_lights`, `infrastructure_light_switch`, `infrastructure_fire_alarm`. |
| Major patterns | `place_building_fixtures()`, `building_layout_signatures.dm`, `building_layout_templates.dm` | Mandatory fixtures must consume reservations and register semantic credits. Random clusters cannot satisfy required program validity. |
| Secondary/detail | `building_layout_fixtures.dm`, `building_layout_microvariation.dm`, `building_layout_macros.dm` | May skip or reduce. Must not change mandatory credits, route, walls or room validity. |
| Facade | `apply_building_facade_rules()` | Apply only after accepted wall/room model; style can reskin but cannot delete function. |
| Validation/repair | `validate_and_repair_building_layout_state()` | Repair may run before acceptance but cannot create fake mandatory rooms/patterns. |
| Score/select | `score_building_layout_candidate()` and quality metrics | Score only ranks candidates that pass mandatory gates. Missing mandatory pattern is not a low score; it is invalid. |
| Emit | `building_layout_emitter.dm` | Emitted plan metadata must match validated state, expose shortages/fallback counters, and fail candidate if emitted turfs/objects diverge from credited state. |

### 1.3. Direction / facing contract

`request.direction` is part of the placement contract, not cosmetic metadata.

`MUST`: `request.direction` affects:

```text
main entry face;
facade entry side;
initial corridor/spine orientation;
public-facing windows/signage;
checkpoint/security approach direction;
counter/console facing where applicable.
```

`MUST`: if direction cannot be honored because selected shape, blockers or footprint feasibility prevent it, generator must either:

```text
choose a declared alternate entry edge and report it;
or fail preview/apply with clear reason.
```

Required metadata:

```text
requested_direction
actual_entry_direction
direction_honored
direction_fallback_reason
```

`REJECT`: direction stored in metadata but ignored by layout.

## Часть C. Геометрия, комнаты и маршруты

### 4. Базовые законы маппинга

Эти правила являются hard constraints. Если генератор их нарушает, результат считается невалидным.

```text
1. У здания есть main_exit.
2. От main_exit есть свободный путь до всех обязательных комнат.
3. Main corridor / hall / loading axis / clear work aisle является reserved_walk.
4. На reserved_walk нельзя ставить dense fixtures.
5. Если route пересекает стену, на этом месте создается floor + airlock/door/opening.
6. Наружные и внутренние стены имеют толщину 1 tile.
7. Запрещены случайные двойные стены и 2x2 wall blocks, если это не явно заданный reinforced block.
8. Запрещены диагональные wall/floor контакты без ортогональной связи.
9. Углы корпуса и комнат должны быть закрыты стеной.
10. Комната 1x1 не является нормальной комнатой.
11. 1x1 допускается только как tiny fixture cell: closet, toilet micro-stall, wall machinery recess, technical nook.
12. Любая кровать, стол, машина, стойка, стеллаж или медоборудование ставится через pattern с clearance.
13. ProgramSpec определяет mandatory rooms и mandatory patterns.
14. Style/Shell preset не определяет функцию здания; он определяет материалы, двери, окна, палитру и faction props.
15. Details slider не влияет на обязательную функциональность.
16. Scatter допустим только для minor clutter/debris/decals/items-on-tables.
17. Validation запускается после каждого ключевого build pass.
```

### 5. Политика shape/footprint

Публичная форма, выбранная пользователем, является контрактом.

Каноническая таблица UI shapes:

| UI shape | Buildable envelope family | Allowed transformation | Минимум для room-capable результата | Hard failure reason |
| --- | --- | --- | --- | --- |
| `point` | `RECT` by `half_width/half_depth` | full rectangle only unless program explicitly chooses family | outer 5x5, normal 7x7+ | too small for exterior wall + room/corridor |
| `line` | `LINEAR_RECT` | widen to corridor/body width, preserve endpoints | width >= 5, length >= 7 | cannot widen without losing selected line intent |
| `polyline` | `LINEAR_COMPOUND` | widen each segment and connect bends | each segment width >= 5, connected | bend/segment cannot produce connected rooms |
| `rectangle` | `RECT` | use selected boundary as shell | outer 5x5, normal 7x7+ | selected bounds too small |
| `filled_rectangle` | `RECT` | same as rectangle, full filled shell | outer 5x5, normal 7x7+ | selected area too small |
| `circle` | `ORTHO_ROUND` | orthogonal stepped envelope inside mask | contains at least one 5x5 room-capable box | no orthogonal room-capable core |
| `ellipse` | `ORTHO_OVAL` | orthogonal stepped envelope inside mask | contains at least one 5x5 room-capable box | no orthogonal room-capable core |
| `ring` | `RING` or `COURTYARD` | preserve inner void as courtyard/loop if wide enough | ring band width >= 3, connected | band too thin or disconnected |
| `diamond` | `ORTHO_DIAMOND` | stepped envelope with closed corners | contains 5x5 core or valid compact variant | diagonal-only wall/floor contacts unavoidable |

| `sector` | `WEDGE` | stepped/wedge envelope, preserve facing | base/core allows public/control axis | no room-capable core |
| `polygon` | `CUSTOM_ORTHO` | orthogonalize user mask and extract envelope | connected room-capable envelope | disconnected/diagonal/thin mask |
| `custom_mask` | `CUSTOM_ORTHO` | use user mask after orthogonal validation | connected room-capable envelope | cannot satisfy walls/corridor/rooms |
| `brush_path` | `LINEAR_COMPOUND` | widen path and create rooms off path | path width >= 5 or side rooms fit | path too thin or fragmented |
| `scatter_cluster` | `COMPOUND` | connect islands by corridors/airlocks | at least two viable islands or one viable core | islands cannot connect without invalid corridor |

`MUST`: any shape advertised by UI must either produce a valid preview/apply candidate or a clear feasibility error. It must not silently fall back to point size or seed-only behavior.


`MUST`: shape support status is evaluated for the current request context:

```text

```

A shape family may be generally implemented, but a specific request may still fail feasibility with clear error.

Example:

```text

```

`MUST`: unsupported shape cannot silently fallback to point/rectangle/random seed behavior.

`MUST`: preview/apply failure reason is user-facing and concrete:


`REJECT`: circle/triangle/polygon/scatter_cluster превращается в обычный прямоугольник без сообщения.

#### 6.1. Room vs Zone

Room = физическое помещение:

```text
имеет bounds;
имеет floor ownership;
может иметь стены/перегородки;
имеет access point;
может иметь door/opening.
```

Zone = смысловая область внутри room:

```text
может не иметь стен;
используется для anchors/pattern placement;
может разделять common room на kitchen_line, living_area, sleeping_nook, dining_area.
```

`MUST`: mandatory RoomSpec означает реальное помещение с bounds/access.

`MUST`: mandatory ZoneSpec означает реальную размеченную область внутри помещения.

`MUST`: нельзя засчитывать комнату, если есть только label без bounds/access.

`MUST`: нельзя засчитывать зону, если она не имеет floor tiles и не может принять свои mandatory anchors/patterns.

Living scale rules:

| Tier | Room/Zone contract |
| --- | --- |
| Compact | `bathroom/sanitation` is a real room; `common` is a real room; `sleeping_nook` may be a zone if bedroom room cannot fit; `kitchen_line` may be a zone inside common. |
| Normal | `bedroom`, `bathroom`, `common/living` are real rooms; `kitchen` may be zone or room by size. |
| Large | multiple bedrooms may be real rooms; kitchen/dining/storage/office may become separate rooms. |

#### 6.2. Required room packing algorithms

The first working implementation must provide these planner families. Unsupported families must produce clear preview/apply errors instead of silent fallback.

##### 6.2.1. Rectangular spine planner

Used for:

```text
living
dormitory
storage
workshop
medbay
kitchen
office
security compact/normal variants
```

Algorithm:

```text
1. Build interior bounds = exterior minus outer wall.
2. Select main_exit on valid exterior edge.
3. Build main spine/hall/loading/work aisle from entry inward.
4. Sort mandatory rooms by priority/privacy/size.
5. Place public/common rooms near entry.
6. Place private/secure/service rooms farther from entry.
7. Attach each mandatory room to spine or allowed open room.
8. Allocate separator wall tiles.
9. Convert required crossings to doors/openings.
10. Validate reachability.
```

##### 6.2.2. Rectangular split planner

Used when building is wider/larger and can support multiple rooms.

Algorithm:

```text
1. Reserve corridor spine or central hall.
2. Split remaining space into left/right/top/bottom room bands.
3. Assign RoomSpecs to bands by min size and adjacency.
4. Merge/split bands if mandatory room cannot fit.
5. Reject candidate if any mandatory room has no access.
```

##### 6.2.3. L/T/U arm planner

Used for explicit `L_SHAPE`, `T_SHAPE`, `U_SHAPE` only.

Algorithm:

```text
1. Decompose footprint into orthogonal arms.
2. Select main arm as circulation spine.
3. Assign public/entry/common to main arm.
4. Assign private/service/storage to side arms.
5. Place doors at arm junctions.
6. Validate no diagonal-only connections.
```

##### 6.2.4. Linear/compound planner

Used for `line`, `polyline`, `brush_path`, `scatter_cluster`, `compound_colony`.

Algorithm:

```text
1. Convert path/islands to connected module graph.
2. Each module must be room-capable or marked connector/service only.
3. Build connector corridors/airlocks between modules.
4. Assign program blocks to modules.
5. Validate global reserved_walk from entry to all mandatory blocks.
```

Pseudo-DM contract:

```dm
/proc/build_room_first_candidate(datum/world_edit_building_layout_state/S)
	if(!resolve_buildable_envelope(S))
		return fail_stage(S, "footprint")
	if(!build_semantic_plan(S))
		return fail_stage(S, "semantic_plan")
	if(!pack_required_rooms_and_zones(S))
		return fail_stage(S, "room_packing")
	if(!build_required_routes(S))
		return fail_stage(S, "corridor")
	if(!build_tile_based_walls_and_doors(S))
		return fail_stage(S, "walls_doors")
	if(!extract_anchors(S))
		return fail_stage(S, "anchors")
	if(!preflight_mandatory_slots(S))
		return fail_stage(S, "semantic_slots")
	if(!place_mandatory_patterns(S))
		return fail_stage(S, "mandatory_patterns")
	return validate_candidate(S)
```

### 7. Коридор и reserved_walk

Коридор это не пустота. Это gameplay route.

Обязательный контракт:

```text
main_exit -> entry/hall -> required room access points
```

Для некоторых программ route имеет другое имя, но тот же смысл:

```text
living: hall
storage: loading_axis
workshop: clear_work_aisle
medbay: triage_to_treatment_route
hydroponics: tray_aisle
security/checkpoint: public_to_secure_control_axis
chapel/ritual: processional_axis
engineering: service_aisle
laboratory: clean_work_aisle
```

Правила:

```text
reserved_walk всегда строится до fixture placement.
dense objects запрещены на reserved_walk.
door cones являются reserved_walk.
если route пересекает internal wall, стена становится door/opening.
route должен flood-fill достигать все обязательные комнаты.
```

`MUST`: `reserved_walk` is a set of concrete floor/door turfs, not just metadata.

`MUST`: every `reserved_walk` turf is walkable in final emitted layout.

`MUST`: every mandatory object has reachable access tile connected to `reserved_walk` or room-local route.

`MUST`: if a corridor passes through a wall/separator, that wall tile is replaced by floor + door/airlock/opening.

`MUST`: dense fixtures, tables, closets, racks, beds, machines and counters cannot occupy `reserved_walk` unless pattern explicitly declares pass-through and validator confirms it is passable.

`REJECT`: corridor report exists, but emitted turfs are blocked.

Definitions:

| Term | Contract |
| --- | --- |
| `access point` | Floor turf inside/at edge of a room that connects to reserved route or room door. Every mandatory room needs at least one. |
| `door cone` | At least the door turf plus one clear floor turf on each passable side. For multi-tile airlocks, every traversed tile is reserved. |
| `clear` | No dense fixture, wall, blocked object, invalid turf, or one-way object that prevents normal player traversal. |
| `route width` | 1 tile for compact buildings, 2 tiles for large/public/loading buildings when footprint allows. |
| `route through room` | Allowed only if that room role is `hall`, `living`, `loading_axis`, `work_aisle`, `greenhouse_aisle`, `ritual_axis`, or explicitly open/public. |
| `multi-door room` | Valid; at least one door must connect to primary route, other doors may connect to service/secondary route. |
| `major fixture access` | Mandatory objects must have an access tile reachable from the relevant room route, not merely be inside the same room bounds. |

Corridor-vs-room zoning:

| Zone kind | Fixture rule | Failure if |
| --- | --- | --- |
| `reserved_strip` | No dense objects. Only door/opening, decals, nonblocking floor detail. | Any dense fixture or wall blocks route. |
| `door_cone` | No dense objects and no object that visually hides the door. | Door has no clear tile on both passable sides. |
| `social_center` | Tables/chairs may exist, but must be outside reserved strip or leave alternate clear route. | `living_table_group` consumes the only route through common/living. |
| `work_zone` | Machines/benches allowed on anchors adjacent to aisle, never on aisle. | Workbench/machine blocks clear work aisle. |
| `storage_zone` | Racks/crates placed beside loading axis, not on it. | Loading axis cannot flood-fill to back/side access. |

Required metrics:

```text
reserved_walk_blocked_count
door_cone_blocked_count
mandatory_room_unreachable_count
mandatory_fixture_access_unreachable_count
```

#### 7.1. Door and opening contract

Door/opening is not decorative. Door/opening is a route transition.

`MUST`:

```text

tile under airlock/door is floor/passable door turf as required by local codebase;
door cone on both sides is reserved_walk;
door dir is cardinal and matches transition axis;
door does not open into dense fixture.
```

Door types are selected by ProgramSpec + StyleSpec:

```text

bathroom -> privacy door

medbay -> medical access/medidoor/glass airlock if available

```

### 8. Стены

Стены строятся не вокруг каждой комнаты отдельно, а из единого floor/room mask.

Правильная модель:

```text
room floors + corridor floors
  -> derived wall candidates
  -> single-thickness wall plan
  -> door/opening override
  -> diagonal/double-wall validation
```

Запрещено:

```text
floor wall wall floor
диагональная стенка без ортогонального угла
дырявый угол корпуса
2x2 wall block от случайного пересечения комнатных рамок
```

Разрешено:

```text
reinforced block только если явно задан role/style/pattern
ruin damage только в damage pass
window/frame только на валидной exterior или intended internal wall
```

#### 8.1. Separator-aware tile model

Логический planner может использовать ownership edges. Финальный DMM/BYOND output всегда tile-based.

```text
Room floors, corridor floors, walls, doors and voids are explicit tile cells.
Internal separator between rooms consumes exactly one tile line.
Door/opening replaces one wall/separator tile with floor + airlock/door/opening object.
```

Allowed relations:

```text
same/open zone:
  floor floor

separated rooms:
  floor wall floor

door crossing:
  floor door floor

outside boundary:
  outside wall floor
```

Forbidden relations:

```text
floor wall wall floor
floor void floor without declared opening/courtyard
diagonal floor contact without orthogonal connection
2x2 random wall block
room frame drawn independently around every room
```

`MUST`: floor cells belong to rooms/corridors; separator intent belongs to edges between cells; final separator output is wall/door/opening turfs.

Правильный wall builder:

```text
1. Назначить owner каждому floor/corridor tile: room_id или corridor_id.
2. Для каждой пары соседних floor tiles проверить owner.
3. Если owner одинаковый, перегородка не нужна.
4. Если owner разный и adjacency declared open-zone, перегородка не нужна.
5. Если owner разный и нужна приватность/граница, ставится ровно один separator.
6. Если corridor/access crossing требует проход, separator превращается в door/opening.
7. Наружная стена строится на границе floor/envelope и outside.
```

Это важно: “стены из единой маски пола” не означает стереть внутренние перегородки. Внутренние стены должны рождаться из room ownership edges and compile into tile-based wall/door turfs, а не из независимого рисования рамки вокруг каждой комнаты.

Tile-level wall emission convention for BYOND turfs:

```text
1. Room bounds and room min sizes describe useful interior floor cells after wall/separator allocation.
2. Separator/wall lanes are reserved during room packing, not stolen from solved mandatory room floors after packing.

5. Exterior walls are emitted from the reserved exterior boundary; rectangular shells must keep closed corner wall turfs.

```

Packing-stage reservation order:

```text

reserve interior room floors
reserve corridor floors
reserve separator lanes where required
reserve door/opening positions
```

Wall emission stage:

```text

does not consume solved mandatory room floors
does not recalculate valid room area from pre-wall bounds
```

`MUST`: room bounds describe useful interior floor cells after wall/separator allocation.

`REJECT`: place solved room floors first, then convert required room floor into wall and still count original room size as valid.

`REJECT`: separator-only debug without correct compilation into tile-based wall/door turfs.
